What the pilot evaluator's metrics measure

The pilot evaluator (eval_code_sha = 1f8a813a…) scored every pilot measurement. This page draws what each of its metrics looks at, on a cartoon of a laparoscopic frame: liver, gallbladder, fat and an instrument, and a prediction that gets each of them wrong in one typical way. Every number on it was computed by the pilot evaluator's own functions when the page was built. The pilot evaluator stays in the private research workbench, so the page cannot be rebuilt here and is kept as it was built. The appendix repeats the metrics on tiny scenes whose numbers were worked out by hand. Where the evaluator specified in docs/evaluation.md changes a behaviour, the page says so.

The frame

The pilot evaluator is given a GT class map (one class per pixel; 0 is unannotated background), the predicted regions (one id per pixel from tracking, with no class; −1 means no region), and the valid pixels, those with a a finite depth greater than 10⁻⁶. Here every pixel is valid. The numbers are those of what the pilot evaluator calls its full domain, every valid pixel; it also reports the object metrics over three narrower domains, which this page does not draw.

1 · Did it find the objects, and how well do they fit? F1@t, SQ, PQ, F1_avg, inst_BF

  1. GT objects are the connected components of each class with at least 300 px; predicted objects are regions with at least 300 px. Background is never an object, and pixels with no region are not a region. The evaluator: a GT object is a class's whole region in the frame, so the two liver pieces below are one object, and there is no minimum size. Background pixels are removed before anything is scored, so a region lying on them, like R4, is neither an object nor a false positive.
  2. Pairs are taken greedily, highest IoU first, each object at most once. A pair with IoU ≥ 0.5 is a hit (TP). An unmatched region is a false positive (FP), and an unmatched GT object a miss (FN).

F1@0.5 counts hits and nothing else: a pair at IoU 0.51 and one at 0.99 score the same. SQ says how well the hits fit. PQ is exactly SQ × F1@0.5. F1_avg, the mean of F1@t over t = 0.50 … 0.95, is fixed to within 0.1·F1@0.5 by PQ and F1@0.5, so it adds nothing. The evaluator keeps F1@0.5, as F1_50, with SQ and inst_BF. It drops F1@0.75 and F1_avg, and does not store PQ, which a table derives from the per-frame SQ and F1_50.

2 · Would the regions give the right class map? GT_mIoU, GT_mDice

Dice is 2·IoU / (1 + IoU) class by class, so GT_mDice repeats GT_mIoU. A tie in the vote goes to the smaller class id. The evaluator keeps mIoU only. It names a region from its scored pixels, so background pixels do not vote, and R4 gets no name.

3 · Are the edges in the right place? boundary_F, P, R and the raw variants

A boundary pixel is one whose left, right, upper or lower neighbour has another label; both sides of an edge are marked, so a boundary is 2 px wide. boundary_F compares the boundaries of the class map from section 2 with the GT's, allowing 2 px. boundary_R_raw and P_raw do the same with the regions themselves, before any class is assigned: an extra cut through an organ costs precision there, never recall. The pilot evaluator also reports tolerances 1, 3 and 5, points on the same curve. The evaluator keeps boundary_F and boundary_R_raw at 2 px. An edge against a pixel it removes, background among them, is not a boundary.

4 · Is anything split or merged? overseg_mean, underseg_error, VI_split, VI_merge

  • overseg counts, per GT class, the regions that each cover at least 200 px and 5 % of it. The pilot evaluator's comment says "or"; the code says "and". A region that merely spills into a neighbour is counted as one of its pieces.
  • underseg_error sums, over every class S and region R touching it, the smaller of |R ∩ S| and |R ∖ S|, divided by the GT area.
  • VI_split = H(regions | GT) and VI_merge = H(GT | regions), in bits, over non-background pixels. Pixels with no region count as a region of their own.

The evaluator keeps VI_split and VI_merge, and drops overseg and UE.

5 · Does a region keep its id over time? time_IoU

An id present in only one of the two frames is skipped, so a region that disappears, or a new one, costs nothing. The evaluator keeps time_IoU as a reference value only, and never gives it a star: coarse regions score well on it. How to score whether a region keeps its identity is not decided yet.

Behaviours to know

  • Thresholds are pixel counts at the evaluation resolution: 300 px for objects; 200 px and 5 % for overseg. The evaluator has no minimum object size, and no overseg.
  • Pixels with no region are no false positive for objects, but they are background in the class map, which moves its boundaries, and a region of their own in VI.
  • CholecSeg8k: the pilot evaluator's colour table gives Hepatic Vein a colour no mask uses, so the class is read as background. The evaluator reads Hepatic Vein from the colour the masks use, and stops on a colour its table does not know.
